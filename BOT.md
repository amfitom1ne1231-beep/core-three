# Бот CoreThree — рабочий инструмент студии

План по итогам опроса заказчика 04.10.2026. Все решения ниже выбраны
им; где решение уточнено при проектировании — сказано почему.

## Кто и зачем

Только команда — трое. Клиенты бота не видят: от студии им достаётся
страница статуса их сайта. Бот — одновременно рабочий чат с кнопками
и админка (Telegram Mini App внутри него). Вход — по Telegram, без
паролей; доступ у всех троих полный, владелец добавляет и убирает людей.

Уведомления — в одну рабочую группу. Темы группы поддерживаются,
но не обязательны.

## Что в нём есть

**Заявки и воронка**
- откуда: форма сайта, почта corethree@mail.ru, вручную из бота
- этапы: Новая → Связались → Созвон / бриф → КП отправлено →
  Договор (заявка становится проектом) или Отказ с причиной
- карточка: кто ведёт, история этапов, заметки, контакт одним нажатием,
  исходный бриф, страница сайта и метки источника
- в группе каждая заявка — сообщение с кнопками «Беру», «Этап»,
  «Заметка», «Отказ», «Открыть»; сообщение обновляется вместе с заявкой
- сроки: в рабочее время через час без «Беру» — повтор в группу
  с отметкой всех; к вечеру без ответа клиенту — тревога владельцу.
  Ночью и в выходные не дёргает

**Клиенты и проекты**
- проект рождается из заявки на этапе «Договор» или вручную
- этапы по шаблону направления (сайт: бриф → прототип → дизайн →
  разработка → запуск → поддержка; бот: сценарий → сборка → интеграции →
  запуск; магазин, мониторинг — свои), у этапа срок
- задачи внутри этапов: исполнитель, срок, статус; напоминание о сроке
  исполнителю через группу
- материалы: ссылки (Figma, репозиторий, диск) и файлы — их пересылают
  боту, он хранит их в самом Telegram и привязывает к проекту
- доступы (пароли к хостингам и панелям) — в зашифрованном поле:
  AES-256-GCM, ключ только в переменных окружения сервера

**Метрики и отчёты**
- в мини-приложении: воронка и конверсия по этапам, заявки по источникам
  и направлениям, время первого ответа, причины отказов, проекты в работе
  и просроченные задачи
- в группу: в будни в 10:00 — новые заявки, что зависло, сроки дня,
  состояние сайтов; в понедельник — итоги недели с цифрами воронки
- источник заявки: сайт начинает передавать страницу входа и UTM-метки;
  Яндекс.Метрика (визиты → заявки) подключается, когда заведён счётчик

**Мониторинг сайтов клиентов**
- каждую минуту — доступность и время ответа, падение подтверждается
  повторной проверкой, чтобы не было ложных тревог
- раз в сутки — срок SSL-сертификата и домена, предупреждение заранее
- инциденты с началом, концом и длительностью; тревога в группу
- у каждого клиента — публичная страница статуса (по образцу демо
  «Лавки») и отчёт за месяц

**Почта и таблица**
- бот читает corethree@mail.ru по IMAP раз в минуту; письма от людей
  становятся заявками, рассылки и уведомления сервисов отсеиваются
- каждая заявка дублируется строкой в Google-таблицу

## Как устроено

```
/            сайт (Next.js) — как был
bot/         сервис: бот, API мини-приложения, расписание, мониторинг, почта
admin/       мини-приложение (React), собирается в статику и отдаётся сервисом
```

- **Один язык — TypeScript.** Бот — grammY, HTTP — Hono, база —
  Postgres через Drizzle с миграциями, мини-приложение — React + Vite
  и официальный SDK Telegram, графики — лёгкая библиотека без тяжёлых
  зависимостей. Тесты — node:test, как у сайта; проверки в GitHub Actions
- **Владелец данных — сервис бота.** Сайт не ходит в базу: заявку
  он передаёт сервису запросом с подписью HMAC. Если сервис недоступен,
  сайт, как сейчас, шлёт заявку прямо в группу — заявка не теряется.
  Supabase уходит
- **База.** На сервере — Postgres 17 в контейнере рядом с сервисом,
  в РФ (152-ФЗ). В разработке и тестах — PGlite: тот же Postgres,
  встроенный в процесс, без Docker. Схема и миграции одни
- **Расписание.** Уточнено при проектировании: вместо pg-boss — своя
  таблица запусков в той же базе. Сервис один, задач немного; ключ
  запуска (`digest:2026-10-05`) не даёт отправить сводку дважды после
  перезапуска, и всё работает на встроенном Postgres в разработке
- **Мини-приложение.** Каждый запрос подписан initData Telegram,
  сервис проверяет подпись и что человек в команде. В браузере без
  Telegram — режим разработки с подставленным пользователем
- **Деплой.** Docker Compose на VPS: сайт, сервис бота, Postgres, Caddy
  (HTTPS сам). Бэкап базы раз в сутки в облачное хранилище в РФ

## Фазы

Каждая заканчивается работающим результатом, который можно потрогать.

1. **Заявки в группе.** Сервис, база, команда и вход, приём заявок
   с сайта, карточка заявки в группе с кнопками, этапы, заметки, отказы
   с причиной, сроки и тревоги. Сайт переходит с Supabase на сервис
2. **Мини-приложение.** Заявки: списки, фильтры, карточка, история.
   Проекты: этапы по шаблону, задачи, материалы, доступы — *готово*
3. **Метрики.** Графики в мини-приложении, утренняя сводка и итоги недели,
   источники заявок с сайта — *готово*, кроме Яндекс.Метрики (нет счётчика)
4. **Мониторинг.** Проверки, инциденты, SSL и домены, страница статуса
   клиента, отчёт за месяц
5. **Почта и таблица.** IMAP, отсев рассылок, Google-таблица
6. **Запуск.** Compose, бэкапы, инструкция по развёртыванию

### Фаза 2 — мини-приложение

**Сделано 04.10.2026 — заявки** (`admin/`, `bot/src/http/auth.ts`, `api.ts`):

- `admin/` — Vite, React, TypeScript, TanStack Query, `@tma.js/sdk-react`
  (пакеты `@telegram-apps/*` из первого плана сняты с поддержки — это
  их прямое продолжение). Собирается в `admin/dist`, сервис отдаёт
  по `/app/`; любой адрес под `/app/` без файла — `index.html`
- экраны: список заявок (в работе по этапам воронки, мои, ничьи, закрытые,
  поиск), заявка (контакт, этап, кто ведёт, бриф, заметка, история, отказ
  с причиной), новая заявка вручную. Маршруты — пути (`/app/leads/12`),
  не якорь: в якоре Telegram передаёт параметры запуска
- вход: заголовок `Authorization: tma <initData>`; сервис проверяет подпись
  (HMAC-SHA256, ключ — HMAC("WebAppData", BOT_TOKEN)), свежесть `auth_date`
  (сутки) и что человек в команде; владелец входит и без `/start`
- API `/api/app/*`: `me`, список с фильтрами, заявка с историей, действия
  `take / stage / lost / reopen / note`, заявка вручную. Всё — через
  `domain/leads.ts`, после действия обновляется карточка в группе
- в группе под карточкой — «Открыть»: ссылка в личку бота
  (`t.me/<бот>?start=lead_12`), там он отвечает кнопкой приложения на эту
  заявку. В личке у команды — кнопка меню «Студия» (`setChatMenuButton`,
  только участникам, не всем подряд)
- **цвета** — только тема Telegram (`--tg-theme-*`), но подтянутые:
  серый текст, ссылки и заливка кнопок в темах Telegram не дотягивают
  до 4,5:1 (белое на `#50a8eb` — 2,6:1), поэтому к ним подмешан цвет
  текста, а кнопка сделана глубже — как в демо «Бритва». Проверено axe
  на темах iOS, Android (тёмная) и Desktop — `admin/src/styles.css`
- **в браузере без Telegram** (`corethree-admin`, порт 5173): `APP_DEV=1`
  в настройках сервиса пускает запросы с этой же машины от имени первого
  владельца. При заданном `PUBLIC_URL` и в production не действует
- **в Telegram до сервера** — туннель: `npm run dev:tunnel` в `bot/`
  (`corethree-bot-tunnel`). cloudflared даёт сервису временный HTTPS-адрес,
  он новый при каждом запуске; сервис сам ставит его в кнопку меню.
  Сервис при этом виден из интернета — наружу открыто только то, что
  закрыто подписью

**Ловушки, на которые уже наступили:**

- web_app-кнопки в inline-клавиатуре работают только в личке — отсюда
  «Открыть» через личку. Прямая ссылка в приложение из группы —

### Фаза 3 — метрики

**Сделано 04.10.2026** (`bot/src/domain/metrics.ts`, `domain/digest.ts`,
`admin/src/screens/Metrics.tsx`, `admin/src/charts.tsx`, `lib/source.ts`):

- **источник заявки.** Сайт при первом заходе во вкладке запоминает
  в `sessionStorage` метки `utm_*`, страницу входа и сайт, с которого
  пришли (`lib/source.ts`, `components/SourceMemo.tsx`), и отдаёт их
  вместе с заявкой. Сервер сайта оставляет только известные поля
  и режет длину; сервис хранит их в `leads.meta`. Политика на сайте
  дополнена (`content/legal.ts`) — **текст политики стоит показать
  заказчику**
- **метрики** считаются из `leads` и `lead_events`, по когорте — заявкам,
  пришедшим за период: воронка («дошли до этапа», включая получившие
  потом отказ), время первого ответа в рабочих минутах (медиана и доля
  в срок), источники, направления, причины отказов, заявки по дням —
  или неделям и месяцам на длинном периоде; проекты — как есть сейчас.
  `GET /api/app/metrics?days=7|30|90|all`
- **экран «Метрики»** — третья вкладка приложения. Графики без библиотеки:
  столбцы по времени (SVG) и списки с полосками. Один цвет от акцента
  темы (`--mark`), проверен скриптом на темах iOS, Android и Desktop:
  на светлой поверхности акцент делается глубже, на тёмной —
  приглушается. Выбор столбца — нажатием или стрелками; числа есть
  и таблицей для читалки
- **утренняя сводка** — в начале рабочего дня, ключ `digest:<день>`:
  кому не ответили, что стоит без движения два рабочих дня и больше,
  сроки дня (бывшее отдельное сообщение `tasks:<день>`). Нечего сказать —
  молчит. Отмечаются только исполнители задач
- **итоги недели** — в первый рабочий день недели, ключ
  `week:<год>-W<неделя>`: цифры прошлой недели теми же формулами,
  что в приложении. Никого не отмечает
- **Яндекс.Метрика** (визиты → заявки) — не сделано: у заказчика нет
  счётчика. Когда появится — `NEXT_PUBLIC_YM_ID` у сайта, а здесь
  останется подтянуть визиты по API Метрики к источникам

### Фаза 5 — почта и таблица

- `imapflow` + `mailparser`, `imap.mail.ru:993`, пароль приложения
  mail.ru в окружении; раз в минуту, последний UID — в `settings`
- отсев: `List-Unsubscribe`, `Precedence: bulk`, `noreply`, известные

### Фаза 6 — запуск

- `docker-compose.yml`: Caddy (HTTPS сам; `corethree.ru` → сайт,
  `bot.corethree.ru` → сервис: `/app`, `/tg/<секрет>`, `/api`), сайт
  (готовый `Dockerfile`), сервис (свой `Dockerfile`: node:22-alpine,
  `npm ci --omit=dev`, `dist/`), Postgres 17 с томом
- сервис — `BOT_MODE=webhook`, `DATABASE_URL`; сайт — `TRUST_PROXY=1`,
  `BOT_INTAKE_URL=http://bot:8787/api/intake/lead`
- бэкап: `pg_dump` раз в сутки в облачное хранилище в РФ; проверить
  восстановление хотя бы раз
- после запуска — место хранения в `content/legal.ts`

### Как здесь принято

- TypeScript у сервиса — 7 (нативный), у сайта — 5.9; проекты раздельные,
  корневой `tsconfig` и ESLint `bot/` и `admin/` не трогают
- общий код сайта и сервиса — `lib/lead.ts` (проверка заявки)
  и `lib/intake-sign.ts` (подпись); сервис импортирует их относительным
  путём, esbuild вшивает при сборке
- логика — в `src/domain` без Telegram и HTTP; тесты — `node:test`
  на PGlite в памяти, бот — с подменённым API (`test/helpers.ts`)
- комментарии и коммиты — по-русски, объясняют «почему»; каждый проход
  записывается в `BRIEF.md`, в конце прохода `main` перематывается
